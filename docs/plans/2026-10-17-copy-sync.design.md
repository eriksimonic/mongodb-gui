# Design: copy, compare and sync of collections and databases

Agreed with the owner on 2026-10-17 in a grilling session, then checked by a review against the backup code and MongoDB behavior. This is the input for `/plan-work`. Three decisions are still open, listed at the end.

## Release 1: copy and production flag

### Copy

- Copy one collection, a chosen set of collections, or a whole database. The target is the same server or another server, with an optional rename of the database or the collection.
- The copy runs `mongodump --archive` piped into `mongorestore --archive`. `packages/app/src/main/backup/tool-process.ts` already pipes stdin and stdout.
- A filter query is allowed per collection. `mongodump --query` takes one collection per run, so each filtered collection gets its own dump. Collections without a filter copy in full.
- When the target collection exists, the dialog offers:
  - Drop and replace (default). Indexes are restored.
  - Merge, which upserts by `_id`. mongorestore has no upsert, so see open question 1.
  - Insert only, which skips `_id`s that already exist. It passes `--noIndexRestore`, because an index with the same name and different options aborts the restore. The result parses the "N document(s) failed to restore" line and shows it as a skipped count, since mongorestore exits 0 in this case.
- Collection-level rename is new. `packages/core/src/backup/restore-args.ts` only emits `--nsFrom=db.*` today, so the rename type gains a `db.coll -> db2.coll2` form, with both parts escaped.
- A copy is blocked when any target namespace equals a source namespace on the same server: no rename, a partial rename, or a swap `a -> b, b -> a`. With `--drop`, mongorestore would drop data that mongodump is still reading. "Same server" means the same hosts and replica set name, not the same profile, because two profiles can point at one cluster.
- Copy reuses the backup compatibility checks against both servers, with 4.2 as the minimum. The tools version has to fit both, so the check takes the intersection of `assessBackup` and `assessRestore`, and blocks when it is empty.
- Renaming a time series collection fails on older tools versions. The check either confirms the tools version supports it or blocks the rename.
- Copy runs as a job in the `backup-service.ts` model: a job id, progress events every 250 ms, and cancel.
- Entry point: right-click on a collection or a database in the tree.

### Production flag

- `production: boolean` (optional) on `ConnectionProfileSchema` and the summary schema in `packages/core/src/schemas/connection.ts`, and a checkbox in the connection editor.
- A connection with the flag shows a red "PROD" badge in the tree and in tab headers.
- Copy, restore and sync into a production connection require typing the target database name. Writes from the editor stay as they are for now.

## Release 2: compare and sync

### Compare

- A new tab type, "Compare". You pick source and target: connection, database, and optionally a collection.
- A database compare matches collections by name. A single-collection compare can pair any two collections.
- It diffs collections (only in source, only in target, in both), indexes, validators and collection options.
- Documents match by `_id`, or by a custom key of one or more fields whose combination is unique (see open question 3). Uniqueness is checked during the compare and again before sync writes. Documents with a duplicate or missing key go to the unmatched bucket.
- The engine streams both sides sorted by the match key and merge-joins them. Both reads use `collation: {locale: 'simple'}`. Core compares keys in BSON order, so `1`, `NumberLong(1)` and `1.0` are equal.
- Equality ignores field order and counts array order, on canonical EJSON. A strict toggle compares raw BSON bytes.
- Buckets: new, removed, changed, identical, unmatched.
- The field-level diff is our own code in core, with no new dependency. It walks both trees and emits added, removed and changed paths.
- On replica sets with MongoDB 5.0 or later, the compare reads with `snapshot` read concern. Older servers and standalone servers use `majority` (or the default on standalone) and show a "not point-in-time" note. A snapshot expires after `minSnapshotHistoryWindowInSeconds` (300 s by default), so `SnapshotTooOld` offers a retry.
- v1 aims at collections under about 1M documents and reads both sides in full. Server-side hashing comes later.
- The renderer holds keys and counts per bucket only. Document bodies and diffs load on demand.
- Compare reports are not stored.

### Sync

- One way, source to target.
- You tick insert, replace and delete separately. All three start unticked.
- Sync reads the source document again at apply time, so results can differ slightly from the report. The summary at the end says so.
- Replace swaps the whole document. When the match key is not `_id`, the replacement has `_id` removed, so the target keeps its own `_id` and MongoDB does not reject the change.
- Insert keeps the source `_id`. If that `_id` already exists on the target under another key, the insert fails and goes to the failed list.
- Delete runs `deleteOne({key, _id: targetId})`. A miss is reported as "skipped, changed since compare".
- Writes go in unordered `bulkWrite` batches, 1000 by default, adjustable in the dialog. Sync keeps going past errors and can be cancelled between batches. Sync is not transactional, so a cancelled or failed run leaves the target partly synced, and a new compare shows what is left.
- When the target collection is empty or missing, sync runs a copy for that collection instead.
- Indexes: unique indexes are created before any data write, and all other indexes after. If a unique index cannot be created on the target, the sync stops and moves no data. This applies to non-empty targets too.
- Deletes and replaces need the target database name typed to confirm. Insert alone gets a plain confirm.

### Special collections

- Views: compared, never a sync target. Sync creates or updates the view definition.
- Time series: copy only, no document sync.
- Capped: compare and insert only. Replace and delete are off.
- `system.*`: always skipped.

### Run log and history

- Every copy and sync run writes a JSON log to the app data folder, encrypted like the rest of the app data. It holds the run header (source, target, options), the counts, and the failed keys with their error codes. It holds no document bodies.
- Logs stay until deleted, up to 100 per source-target pair. The oldest go first.
- A "Sync history" list in the Compare tab opens past logs.
- "Retry failed" syncs only the failed keys, reading the source again at that moment.
- Each failed document gets a resolution, per row or for all rows with the same error. Resolutions run as one more batched sync and log to the same run.
  - An `_id` collision: insert with a new `_id`, overwrite the target document that holds this `_id`, or skip.
  - A unique index violation: overwrite the conflicting target document, or skip.
  - A validator rejection: skip, or edit the document and retry.

## Open questions

1. Merge in copy. mongorestore cannot upsert. Recommendation: merge uses the driver's batched `replaceOne` upsert writer, which release 1 then builds early. The other choice is to leave merge out of release 1.
2. Cancel during drop and replace leaves the target half-filled, with the old data gone. Recommendation: restore into a temporary name and `renameCollection` over the target at the end, within one database. Across databases the rename is a copy, so the confirm dialog shows a warning instead.
3. Custom key and indexes. A sort on a field without an index hits the 100 MB in-memory limit, and `find` on 4.2 cannot spill to disk. Recommendation: a custom key requires a unique index on both sides. `_id` always works.
